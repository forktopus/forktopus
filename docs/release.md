# Выпуск релиза

Файлы выпуска собирает CI, публикует их владелец командой `go run ./scripts/release` (`scripts/release/`). Скрипт не собирает приложение и не меняет код, кроме коммита версии в `bump`. Порядок для агента — скилл [`forktopus-release`](../.agents/skills/forktopus-release/SKILL.md).

## Что нужно

- Git с доступом к `origin` = `github.com/forktopus/forktopus`.
- Авторизованный GitHub CLI `gh`. Вход и токен — забота `gh`, скрипт их не читает.
- Go для `go run`. Сборочное окружение не нужно: Linux, Windows и macOS собирает CI.

## Как CI собирает файлы

`.github/workflows/ci.yml` на push и PR запускает проверки на Linux. Это формат, типы, тесты фронтенда, актуальность bindings, `go vet` и `go test`. На push в `main` с изменениями приложения и при ручном запуске (`gh workflow run CI --ref main`) после проверок три job собирают файлы скриптом `scripts/release.sh --os <ос>` на своей ОС:

| Артефакт | Файлы | Где собран |
|---|---|---|
| `forktopus-linux` | `forktopus_<v>_amd64.deb`, `Forktopus-<v>-x86_64.AppImage` | `ubuntu-24.04` |
| `forktopus-windows` | `forktopus-<v>-windows-amd64-setup.exe` (установщик NSIS), `forktopus-<v>-windows-amd64.exe` | `windows-latest` |
| `forktopus-macos` | `Forktopus-<v>-macos-universal.zip` (`.app` с ad-hoc подписью) | `macos-latest` |

CI не запускается, если коммит меняет только документацию и вспомогательные файлы: корневые `*.md`, `LICENSE`, `docs/`, `assets/`, `.claude/`, `.agents/`, `.vscode/`, `compose.dev.yaml`, `docker/` и лендинг `www/` (его публикует workflow Pages). Также исключены `.github/ISSUE_TEMPLATE/` и `.github/pull_request_template.md`. Список — в `paths` workflow. Если изменены только workflow (в том числе вместе с перечисленными файлами), проверки выполняются, а сборки файлов поставки пропускаются. Для определения изменений сравнивается весь диапазон push; если сравнение невозможно, сборки выполняются. Чтобы выпустить коммит без собранных файлов, запустите CI вручную: `gh workflow run CI --ref main`. Ручной запуск всегда выполняет и проверки, и сборки; повтор обычного запуска без сборок их не добавит.

В каждом артефакте есть свой `SHA256SUMS`. Артефакты хранятся 30 дней. Выпуск из более старого коммита требует перезапустить его CI: `gh run rerun <id>`.

Версия приложения записана в `build/config.yml` и ещё в десяти файлах `build/`: манифестах, plist и nfpm. CI собирает ту версию, которая закоммичена.

## Порядок

1. **README.** Перед выпуском README приводится в соответствие с ним: версия в строке «Статус», таблица «Установка» (ровно файлы выпуска), «Что умеет» и «Известные ограничения». Правки — отдельным коммитом до `bump`: коммит только с документацией CI не запускает, файлы соберёт CI коммита версии. Если версия уже закоммичена, после правок README запустите CI вручную.

2. **Версия.** Команда

   ```bash
   go run ./scripts/release bump --version X.Y.Z
   ```

   требует чистого дерева. Она меняет версию во всех файлах `build/` и создаёт коммит `build: версия X.Y.Z`. Затем выполните `git push origin main` и дождитесь зелёного CI этого коммита (`gh run watch`).

3. **План.** Команда

   ```bash
   go run ./scripts/release plan [--version X.Y.Z]
   ```

   только читает Git и GitHub. Без `--version` она предлагает следующий patch после последнего опубликованного релиза, а для первого выпуска — версию из `build/`. Результат — JSON:
   - `previousTag`, `commits` и `changes` (`diff --stat`) от предыдущего опубликованного релиза;
   - `appVersion` и `versionCommitted`: совпадает ли версия в `build/` с выбранной;
   - `workingTreeClean`, `remoteMainMatches`;
   - `ci` и `ciRun`: последний запуск CI этого коммита на push или вручную;
   - `releaseState`, `remoteTagExists`, `prepared`.

   Предыдущий выпуск определяется по опубликованным релизам, а не по локальным тегам.

4. **Описание** пишется по-русски в `bin/release/notes-X.Y.Z.md`. Каталог `bin/` не попадает в Git.

5. **Подготовка.** Команда

   ```bash
   go run ./scripts/release prepare --version X.Y.Z --notes bin/release/notes-X.Y.Z.md
   ```

   проверяет условия:
   - дерево чистое;
   - версия в `build/` равна X.Y.Z;
   - X.Y.Z выше последнего опубликованного релиза;
   - CI этого коммита (на push или вручную) успешен.

   Затем команда ставит локальный аннотированный тег `vX.Y.Z` на HEAD и скачивает артефакты этого запуска (`gh run download`). Каждый файл сверяется с `SHA256SUMS` своего артефакта. Комплект складывается в `bin/release/vX.Y.Z/`:
   - пять файлов поставки;
   - общий `SHA256SUMS`;
   - `notes.md`;
   - `release.json` с коммитом, номером запуска CI, размерами и SHA-256 файлов.

   На GitHub команда ничего не отправляет. Повторный `prepare` с тем же описанием переиспользует готовый комплект. Если комплект собран с другим описанием или из другого коммита, команда отказывает. Каталог незавершённой подготовки удаляется вручную.

6. **Публикация.** Команда

   ```bash
   go run ./scripts/release publish --version X.Y.Z
   ```

   требует чистого дерева и HEAD, совпадающего с `main` на GitHub. Исходный коммит комплекта должен быть в его истории. Порядок работы:
   1. Сверяет комплект с `release.json`.
   2. Отправляет тег.
   3. Создаёт черновик `Forktopus X.Y.Z` с описанием (`gh release create --verify-tag --draft`).
   4. Загружает недостающие файлы без `--clobber`.
   5. Сверяет `size`, `state` и `digest` каждого вложения через GitHub API. Вложения обратно не скачиваются.
   6. Публикует релиз как latest и заново проверяет вложения по версионным адресам.

   Квитанция сохраняется в `bin/release/vX.Y.Z/public-release.json`.

После сетевого сбоя `publish` можно повторить. Совпадающие вложения остаются, недостающие догружаются. Пустой `starter` от оборванной загрузки удаляется, но только в черновике. Для опубликованного релиза повторный `publish` только проверяет вложения.

Релизы репозитория неизменяемые (immutable releases): после публикации файлы релиза нельзя заменить или удалить, а его тег — перенести. Черновик менять можно. Теги `v*` дополнительно защищены ruleset «Теги выпусков»: их нельзя удалить или перенести, даже если релиза ещё нет. Ошибку в опубликованном выпуске исправляет только следующая версия.

Скрипт никогда не делает следующего:
- не перезаписывает опубликованные файлы и теги;
- не понижает latest на более старую версию;
- не публикует, если описание или имя существующего черновика отличаются от комплекта.

## Проверка скрипта

```bash
go test ./scripts/...
```

Тесты работают на временном origin и подменённом GitHub. Они проверяют такие сценарии:
- первый выпуск;
- смену версии;
- отказ без зелёного CI;
- повтор `prepare`;
- обрыв загрузки;
- несовпадение digest;
- повторную проверку опубликованного релиза.

Эти тесты входят в CI.
