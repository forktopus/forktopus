# Релиз Forktopus

Работай в корне репозитория Forktopus. Механику выполняет `go run ./scripts/release`. Порядок, требования и состав выпуска описаны в `docs/release.md`. Если эта памятка с ним расходится, верен документ. Другие репозитории не меняй.

## Версия и описание

1. Выполни `go run ./scripts/release plan`. Если пользователь назвал версию — `go run ./scripts/release plan --version <версия>`. Команда только читает Git и GitHub. Незакоммиченные изменения ей не мешают, но в выпуск они не войдут: план относится к HEAD.
2. Возьми из результата `previousTag`, `previousRevision`, `revision`, `commits` и `changes`. Посмотри существенный diff от `previousRevision` до `revision`. Сообщения коммитов сами по себе не доказывают, что возможность есть.
3. Предложи SemVer `X.Y.Z` без `v`:
   - patch — для исправлений;
   - minor — для новых возможностей;
   - major — для несовместимых изменений, например формата настроек или кэша без миграции.

   Версия в плане — только начальная рекомендация: следующий patch после последнего опубликованного релиза. Существующий выпуск без прямого поручения не переиздавай.
4. Сверь README с выпуском до `bump` (тот требует чистого дерева):
   - строка «**Статус:**» — новая версия и то, где сборка действительно проверялась;
   - таблица «Установка» — ровно файлы выпуска (раздел «Состав выпуска» ниже) и примечания к ним;
   - «Что умеет» и «Известные ограничения» — по существенному diff выпуска; то же для `docs/`.

   Правки закоммить отдельно (`docs: README к выпуску X.Y.Z`) в рамках поручения выпустить версию. Коммит только с документацией CI не запускает, его соберёт CI коммита версии. Если версия уже закоммичена, после такого коммита запусти CI вручную: `gh workflow run CI --ref main`.
5. Если `versionCommitted` равно false, версию в `build/` меняет `go run ./scripts/release bump --version X.Y.Z`. Команда создаёт коммит, поэтому выполняй её только в рамках поручения выпустить версию. После неё нужны `git push origin main` и зелёный CI этого коммита. Сборка в CI занимает несколько минут: жди `gh run watch <id>` в фоне.
6. Напиши описание по-русски и сохрани в `bin/release/notes-<версия>.md`.
   - Для следующих выпусков опиши полезные пользователю изменения с предыдущего выпуска, действия при обновлении и известные ограничения, если они действительно есть.
   - Пустые разделы не добавляй. Внутреннюю историю разработки (шаги плана, рефакторинг, тесты) не переноси.
   - Таблицу установки делай с прямыми версионными ссылками `https://github.com/forktopus/forktopus/releases/download/v<версия>/<имя-файла>`.

## Состав выпуска

Пиши как в таблице «Установка» README:

- Linux:
  - `forktopus_<версия>_amd64.deb` — Ubuntu 24.04+ / Debian 13+, `sudo apt install ./…`;
  - `Forktopus-<версия>-x86_64.AppImage` — другие Linux x86_64, `chmod +x` и запустить.
- Windows, x64, Windows 10/11:
  - `forktopus-<версия>-windows-amd64-setup.exe` — установщик для текущего пользователя без прав администратора: ярлыки, удаление через «Приложения», при необходимости WebView2 Runtime;
  - `forktopus-<версия>-windows-amd64.exe` — без установки, нужен WebView2 Runtime.
- macOS: `Forktopus-<версия>-macos-universal.zip` — `.app` для Intel и Apple Silicon с ad-hoc подписью. Apple его не нотаризовала, поэтому Gatekeeper не даст открыть его двойным щелчком. Снять карантин: `xattr -cr forktopus.app`.
- `SHA256SUMS`.

Код не подписан сертификатом: Windows SmartScreen предупредит о неизвестном издателе.

Сведения о проверенных платформах сверяй с разделами «Статус» и «Известные ограничения» в [README](../../../README.md). Для версии 0.3.1 подтверждена работа на Windows 11 в виртуальной машине (включая установщик, `gh`, `glab`, `gt`) и macOS Sequoia 15.7.7. Не своди проверку Windows к локальной части и не называй macOS непроверенной. Проверки конкретной версии не переноси автоматически на другие версии, обе архитектуры Mac или отдельные сценарии без подтверждения.

## Подготовка и публикация

Учитывай точный объём поручения:
- Просьба спланировать выпуск или написать описание не разрешает `bump`, `prepare` и `publish`.
- Явное поручение выпустить согласованную версию разрешает все команды. Повторно разрешения не спрашивай.
- Прямой запрет на коммиты, теги или публикацию важнее.

`prepare --version <версия> --notes bin/release/notes-<версия>.md`:
- требует чистого дерева, версии в `build/` и успешного CI этого коммита (на push или ручного);
- ставит **локальный** тег, скачивает артефакты CI и собирает комплект в `bin/release/v<версия>/`;
- на GitHub ничего не отправляет.

Если CI в состоянии `pending`, дождись его. Если `failure` или `absent`, назови причину и предложи `gh run rerun <id>` или push. Коммит только с документацией CI не запускает: для него предложи `gh workflow run CI --ref main`. Проверку не обходи и не собирай файлы локально вместо CI.

`publish --version <версия>`:
- выполняй только в рамках поручения выпустить эту версию;
- HEAD должен совпадать с `main` на GitHub;
- команда отправляет тег, создаёт черновик `Forktopus <версия>`, загружает файлы и сверяет каждый, затем публикует релиз как latest и проверяет вложения ещё раз.

Релизы неизменяемые, теги `v*` защищены ruleset от удаления и переноса: опубликованный выпуск исправляет только следующая версия.

При сетевом сбое повтори ту же команду один раз. Если отказ повторился, остановись и назови этап. Несовпадение SHA-256, описания или Git-состояния требует разбирательства. Не удаляй релиз, не используй `--clobber`, не переноси тег и не собирай заново под опубликованным номером.

Вложения проверяются только по метаданным GitHub API: `digest`, `size`, `state` и версионный URL. **Не скачивай вложения обратно для проверки.**

## Изменения скрипта

После правок `scripts/release/` запусти `go test ./scripts/...`. Тесты работают на временном origin и подменённом GitHub; настоящий релиз они не создают.
